# Автодеплой на игровой сервер

Служба `mcombat-deploy` работает на сервере. Каждые 20 секунд она спрашивает GitHub, какой последний коммит лежит в ветке `master`. Если коммит новый и все проверки GitHub по нему прошли, служба забирает его и запускает `deploy/release.sh`. Если выпуск не удался, она возвращает предыдущую версию.

## Установка (один раз, от root)

```bash
curl -fsSL https://raw.githubusercontent.com/abieahma/mcombat/master/deploy/install.sh | sudo bash
```

Скрипт ставит git, curl и jq, кладёт копию репозитория в `/opt/mcombat/repo` и создаёт настройки `/etc/mcombat/deploy.env`, затем включает службу. Для контейнеров серверу понадобится Docker, его нужно поставить отдельно.

## Как проверить

- Состояние службы: `systemctl status mcombat-deploy`
- Лог в реальном времени: `journalctl -u mcombat-deploy -f`
- История выпусков: `/var/lib/mcombat/deploy.log`
- Какой коммит сейчас развёрнут: `/var/lib/mcombat/deployed_sha`

## Настройки (`/etc/mcombat/deploy.env`)

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `BRANCH` | `master` | Какую ветку разворачивать |
| `INTERVAL` | `20` | Как часто проверять GitHub, в секундах |
| `REQUIRE_CI` | `1` | `1` — разворачивать только коммиты, прошедшие проверки GitHub |
| `GITHUB_TOKEN` | пусто | Токен только для чтения, поднимает лимит запросов к GitHub API |

После изменения настроек: `systemctl restart mcombat-deploy`.

## Что происходит при выпуске

1. Служба переключает копию репозитория на новый коммит.
2. Запускает `deploy/release.sh` из этого коммита. Шаги выпуска лежат в репозитории и меняются вместе с кодом.
3. Если `release.sh` завершился с ошибкой, служба возвращает предыдущий коммит, запускает его `release.sh` и пишет в лог `FAILED`. Неудачный коммит она больше не трогает, пока в `master` не появится следующий.
4. Если изменился сам `deploy/watch.sh`, служба перезапускается с новой версией.

Пока в репозитории нет `server/compose.yaml`, выпускать нечего, и `release.sh` просто сообщает об этом.
